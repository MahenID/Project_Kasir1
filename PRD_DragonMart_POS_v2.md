## 1. Product Context and Outcomes

### 1.1 Context and evidence limits

The owner wants to rebuild a cashier project originally developed during semester 3. The original PRD describes `projectkasir_old` / `kasirdragon` as a PHP Native application with MySQL, products, suppliers, customers, employees, sales, and reports. Those descriptions are legacy claims supplied by the original document. The legacy source code and SQL dump were not available for this revision.

Do not repeat claims about plaintext passwords, exploitable SQL injection, actual transaction limitations, or performance as verified findings until the relevant source is inspected. A legacy audit must identify the file, code location, source version, observed behavior, and evidence. Missing loyalty features, one preferred supplier, or an uncached query are not automatically defects.

Keep the legacy project unchanged as a reference. The default release uses new test data and approved opening inventory; historical-data migration is an optional separate deliverable.

### 1.2 Intended outcomes

1. A cashier can sell multiple products in one checkout with predictable totals and change.
2. A completed sale has consistent items, payment, stock movements, and shift attribution.
3. Concurrent cashiers cannot oversell the same stock; retries cannot duplicate a sale.
4. Managers can trace receiving, adjustments, counts, returns, and cash differences.
5. Receipts and reports remain correct when current product prices, names, or store settings change.
6. The project can be installed, tested, backed up, and restored using documented procedures.

Product correctness takes priority over optional infrastructure or visual polish.

Additional rules:

- At least one active owner must remain. Users with financial history are deactivated, not hard-deleted.
- A manager cannot change their own role, create another manager, change an owner, or grant permissions.
- Owner/manager approval is an authenticated server action, not a shared supervisor PIN. Such users may approve their own requests; this exception is recorded in the audit event.
- A cashier's return lookup reveals only receipt/item/refund eligibility data, never cost or unrelated customer information.
- Prevent account or terminal deactivation while its shift is open. Sessions for deactivated accounts must be invalidated; temporary operational recovery follows an audited owner procedure.

## 5. Sales Calculations and Checkout Contract

### 5.1 Numeric rules

- IDR selling prices, discounts, taxes, payments, and refunds are stored as integer rupiah (`BIGINT`). Maximum whole-sale total is IDR 1,000,000,000. Reject overflow and amounts outside the declared limits.
- Quantities are positive integers for sale/receiving/return lines; inventory balances are nonnegative integers. A sale has 1–100 distinct product lines, each with quantity 1–10,000, subject to stock availability.
- Average unit cost uses `DECIMAL(20,6)` and extended cost uses `DECIMAL(24,6)`. Use decimal/integer arithmetic in backend calculations, never binary floating-point as the monetary authority.
- Percentage inputs use integer basis points: 100 basis points = 1%. Rates range from 0 to 10,000 basis points. This is an input range, not a prescribed tax rate.
- `round_half_up` rounds to the nearest whole rupiah; an exact positive half rounds upward. Cost results round half-up to six decimal places. JSON monetary/cost fields are decimal strings; quantities/rate basis points are integers.
- Zero-price products are allowed only when explicitly configured by owner/manager and audited. A zero-total sale uses cash with zero tender/change; it remains a completed sale, not a missing payment.

### 5.2 Discount and tax order

For line `i` with quantity `Q_i` and price `P_i`:

1. `gross_i = Q_i × P_i`.
2. An item discount is either a fixed amount for the entire line or a percentage of `gross_i`, rounded half-up. It cannot exceed `gross_i`.
3. `base_i = gross_i − item_discount_i`.
4. A sale discount is either a fixed amount or a percentage of `sum(base_i)`, rounded half-up. It cannot exceed that sum.
5. Allocate the sale discount proportionally to `base_i`, flooring each allocation and distributing the remaining rupiah by largest fractional remainder; ties use ascending product ID. Zero-base lines receive no allocation. If the whole base is zero, the sale discount must be zero.
6. `net_i = base_i − allocated_sale_discount_i`.
7. With exclusive tax enabled, `tax_i = round_half_up(net_i × tax_rate_bps / 10000)`; otherwise zero. Version 1 uses one store-wide rate for all products.
8. `line_total_i = net_i + tax_i`; `grand_total = sum(line_total_i)`.

Persist gross amounts, item discount type/input/amount, allocated sale discount, net amounts, tax rate/amount, cost snapshots, and totals. Historical returns and reprints use these snapshots.

Cashier discount defaults are zero. Owner configures per-role item and sale discount limits, including percentage and absolute bounds. Both bounds apply when configured; combined item-plus-sale discounts must also satisfy the configured effective maximum for each line. Backend checks the effective discount, not only the input representation. No temporary shared PIN bypass is supported.

### 5.3 Quote and successful checkout

1. The cashier has an active account and their own open shift on an active terminal.
2. The client requests a quote using product IDs/quantities, requested discount inputs, customer ID, and shift ID. Prices, cost, tax, actor, and terminal identity are resolved by the server.
3. The server validates limits and permissions, returns totals and availability, and issues an opaque `quote_id` valid for 120 seconds. The quote belongs to the user/shift and reserves no stock.
4. The cashier selects one payment method. For non-cash, they verify external success and enter reference/confirmation. The UI must label this as manually confirmed.
5. The client generates a checkout UUID and submits `quote_id`, `shift_id`, and payment data with `Idempotency-Key`. The canonical payload and key are retained until the outcome is known.
6. The backend validates the key's ownership/payload, then performs the inventory-control check and locks the shift and affected products. Recheck active state, product/price/setting versions, stock, permissions, payment sufficiency, and quote lifetime. If commercial conditions changed, return `QUOTE_CHANGED` with a new quote; do not silently accept changed prices.
7. In one database transaction, consume the quote, create the sale/items/payment, decrease stock, record movements and the authoritative domain audit event, and store the successful idempotency outcome.
8. Commit before starting receipt printing, optional notifications, or export work. The response includes sale ID, receipt number, totals, and receipt URL.

Commercial revalidation covers products and tax/discount settings; a quote that expires before submission must be renewed. A replay of an already successful key returns its original sale even if that quote is now expired or the shift closed, after current authentication and read authorization.

### 5.4 Concurrency and idempotency invariants

- Use row locks or a demonstrably equivalent conditional update. Client availability indicators and cached catalogs are advisory only.
- Use a consistent locking order: idempotency/operation record, inventory-control guard if relevant, shift, source document, then product rows ordered by product ID. Validate behavior on MySQL/InnoDB, not only SQLite.
- The inventory-control guard must prevent a stocktake pause being enabled between an operation's pause check and stock commit. A shared/exclusive database guard or equivalent is acceptable; do not hold a database transaction open while a person counts stock.
- Unique scope for keys is `(user_id, operation, key)`; store a canonical payload hash. A reused key with another payload returns `IDEMPOTENCY_CONFLICT`.
- A duplicate successful request returns the same resource and values. Concurrent identical requests serialize or return a recoverable in-progress response; they cannot execute twice.
- Validation failures do not commit business records. After correcting a rejected request, use a new key and quote. During an unknown outcome, reuse the original key and payload only.
- On a transaction rollback, all sale/payment/stock/quote-consumption changes roll back. A deterministic success mapping is retained for the sale's retention period; it is not pruned after a short cache TTL.
- Deadlock retries are bounded to three database attempts and reuse the same logical operation. Failure returns a recoverable error without partial postings.

### 5.5 Payment and failure behavior

For cash: `tendered >= grand_total`, `applied_amount = grand_total`, and `change = tendered − grand_total`. For manual non-cash: `applied_amount = grand_total`, tendered equals total, and change is zero. Do not send/store card PAN, CVV, or payment credentials.

| Condition | Required behavior |
|---|---|
| Insufficient stock | Return `INSUFFICIENT_STOCK`; commit no sale, payment, or movement. |
| Insufficient cash tender | Validation failure; preserve cart; no posting. |
| Price/tax/permission change | Require a fresh accepted quote. |
| Inventory paused | Reject checkout explicitly; preserve cart. |
| External manual payment succeeds but POS posting fails | Show an unresolved external-payment warning with reference and checkout key; operator checks recovery before retry and arranges external reversal if sale cannot be posted. Do not request payment again automatically. |
| Response lost after commit | Recovery or identical retry retrieves the original sale. |
| Printer unavailable | Keep sale completed; offer receipt view/reprint. |
| Session expires | Reauthenticate the same user, then recover the key before another checkout. |

Manual confirmation does not provide provider reconciliation guarantees. Gateway integration is a separate release with its own provider state machine, callback signature checks, idempotency, and reconciliation.

## 6. Lifecycle Rules, Returns, and Cash

### 6.1 Document states

| Record | Allowed lifecycle | Posting effect |
|---|---|---|
| Local cart / server quote | Local editable cart; unconsumed, consumed, or expired quote | No stock/payment posting. |
| Sale | Created as `completed`; derived return status `none`, `partial`, or `full` | Exactly one original successful payment. Original sale is immutable. |
| Original payment | `recorded`, then derived `partially_refunded` or `refunded` | Original applied amount is immutable; linked refunds provide offsets. |
| Receiving / opening | `draft → posted` or `draft → cancelled` | Stock changes only on posting. |
| Stock adjustment / revaluation | `draft → posted` or `draft → cancelled` | Quantity and/or current cost changes only on posting. |
| Stocktake | `counting → posted` or `counting → cancelled` | Store inventory pause active while counting. |
| Return request | `requested → approved → completed`; requested may be rejected/cancelled; approved may be cancelled | Financial/stock changes only on completion. |
| Shift | `open → closed`; review status separately pending/acknowledged | Closed figures immutable. |
| Export job | `queued → running → ready` or `failed` | No effect on source business records. |

Version 1 has no persistent unpaid sales, online payment-pending state, or hard deletion of a completed sale. A checkout abandoned before posting is a cart cancellation. A completed sale correction uses a linked return/refund; full reversal is recorded as a full return with a correction reason.

### 6.2 Partial and full return rules

- Default return window is seven calendar days in store timezone, configurable by owner. Eligibility compares server event times; owner may explicitly override an expired window with a reason and an audit event.
- Each return line references one original sale item and specifies whole quantity, reason, and `restockable` or `damaged`. One request may split an original line by disposition; the combined quantity is checked.
- Approval binds the exact content hash. Editing or reassigning an approved request invalidates approval and requires a new request. Approval expires 24 hours after approval; an expired request remains visible and requires reapproval before completion.
- Draft/approved requests do not reserve returnable quantity. Completion locks the original sale and rechecks remaining quantities against all completed returns; simultaneous requests cannot over-return.
- For a sold line of `Q` units and original amount component `M` (net or tax), cumulative refund for `k` completed returned units is `round_half_up(M × k / Q)`. A new return refunds the difference between the new cumulative value and the previous cumulative value. This preserves every original rupiah and prevents rounding drift.
- Restockable returns add stock at the original sale unit-cost snapshot and update current weighted average. Damaged returns add no sellable stock. For this operational costing policy, reverse COGS only for restockable quantities; damaged returned quantities remain expensed in original COGS and are reported separately as non-restocked returns.
- Complete through a currently authenticated permitted operator's own open shift. A cashier may complete only an approved request; the server verifies approver role, content, expiry, and remaining quantity. Owner/manager may request and approve their own return, with an explicit audit marker.
- Cash refund requires enough expected drawer cash and physically available cash; otherwise arrange an audited cash-in first or decline completion. The operator confirms the counted amount and intent, posts the refund, and hands over the cash only after a successful response or recovery confirms completion. An unknown response must be recovered before payout or another refund attempt. If a confirmed payout cannot be physically completed, record an owner/manager incident for reconciliation; never create another refund automatically. Refunds are applied to the current handling shift, even when the original sale's shift is closed.
- Non-cash refund uses the original method, has a required external reversal/refund reference, and is manually confirmed as completed. No sellable-stock or refund posting occurs while that external action remains unresolved.
- If an externally completed refund is followed by a failed or unknown local posting, preserve its external reference, approved request, payload, and operation key. Recover or retry that local operation without initiating another external refund. Escalate unresolved differences to owner/manager reconciliation.
- Return lines, one refund, stock effects, sale/payment derived return status, audit event, and idempotency outcome commit together. Completed returns cannot be cancelled or edited.

### 6.3 Shifts and drawer reconciliation

1. Opening requires an active terminal, no other open shift for that terminal/user, and starting cash of at least zero. Enforce these rules under concurrent requests using database-backed uniqueness/locking.
2. Opening cash is the counted float. It is not a sale and is not an additional cash-in record.
3. Cash in/out is positive, reasoned, and attributed to a specific open shift. Cash out cannot exceed expected cash. No cash movements are automatically counted as business income or expense.
4. Expected cash = starting cash + original cash applied amounts − completed cash refunds + cash in − cash out. Tender minus change equals the sale's cash applied amount; do not count the entire tender as retained cash.
5. Non-cash payments/refunds do not change the physical drawer. Net collected payment reports include them separately.
6. The X report is a current preview and does not close or reset the shift. At closure, record actual counted cash, server-calculated expected cash, difference `actual − expected`, and a required explanation if difference is nonzero.
7. Shift closure locks the shift against concurrent checkout/refund/cash movement. If closure wins first, those operations must fail without posting.
8. The Z report snapshots totals and cannot change after closure. Owner/manager append review notes; review does not modify sales or cash counts.
9. A shift may cross midnight. It retains one shift identity; calendar reports group each sale/refund by its own event time. Session logout/expiry does not close it.
10. A replacement cashier closes the prior shift through an owner/manager-assisted, audited closure with a physical count, then opens a new shift. No silent transfer or reopening is allowed.

## 7. Inventory Rules and Costing

### 7.1 Receiving and opening inventory

A purchase receiving document requires an active supplier, external document reference when available, receiver, received date, and at least one line with product, positive quantity, and nonnegative acquisition unit cost. Opening documents have no supplier and are clearly labelled opening balances. Snapshot source SKU/name/unit and acquisition cost. A supplier document reference duplicated for the same supplier requires an explicit manager warning acknowledgment and reason; it is not assumed globally unique.

Acquisition cost is entered as the cost attributable to inventory; store staff are responsible for its business treatment. Version 1 does not calculate supplier tax credits, freight allocation, accounts payable, or statutory accounts.

For current quantity `q`, current average cost `c`, received quantity `r`, and acquisition cost `p`:

`new_average = round_to_6_decimals((q × c + r × p) / (q + r))`.

When `q = 0`, the new average is the new acquisition cost. Selling stock does not change average unit cost. At zero quantity the last average may be retained as a reference, but inventory value is zero. A subsequent receipt recalculates from its acquisition cost.

Post each document exactly once, with its lines and stock movements in one transaction. Posted documents are immutable. Correct a posted mistake through a separately reasoned quantity adjustment and, where cost is wrong, an owner-only revaluation; retain references to the erroneous receipt. This operational correction does not retroactively recalculate past sales or constitute a full purchasing accounting reversal.

### 7.2 Adjustments and valuation

- Directly updating `products.stock` through product CRUD is prohibited.
- Quantity adjustments use signed quantity and current average cost; record actual before/after balances. They do not create sale revenue.
- Positive adjustments may use retained current average cost. If that cost is zero and the counted goods have a known nonzero cost, resolve through an opening/receiving document or owner revaluation; do not silently infer cost.
- Owner-only revaluation sets a nonnegative current average cost with a reason, evidence reference, and before/after inventory value. Its movement has zero quantity and an explicit `revaluation` type.
- Current inventory value = current sellable quantity × current average cost. Adjustment/revaluation gains/losses appear in inventory reports, outside gross sales profit.
- All posting pathways, including returns and stocktake, use the same stock service and append immutable movements atomically. Cached stock must never authorize a sale.
- Product archival preserves balances/history. Remaining stock must still appear in stock/valuation/count reports even when the product is not sellable.

### 7.3 Stocktake

The initial implementation pauses all store inventory writes for a scheduled count. Checkout, receiving, adjustments, revaluations, and return completion are blocked; reads, return preparation, and shift closure can continue.

Starting a count captures system quantities and includes all active products plus archived products with remaining stock. An inventory guard makes starting the pause atomic with respect to in-flight writes. Counts are editable while the document is counting; every included product requires an explicit nonnegative count, including explicit zero. Posting locks affected products, verifies the snapshot and pause ownership, writes difference movements at current cost, and releases the pause in the same transaction. Cancelling releases it without movements. Owner/manager may recover an abandoned count by audited cancellation, not by editing a flag directly.

## 8. Reporting Definitions and Historical Integrity

### 8.1 Dates and values

Store database event timestamps in UTC with sufficient precision; display and filter in the configured store timezone. Calendar reports use a half-open UTC interval derived from the selected local start date and the day after the local end date. Server time is authoritative. Backdating posted sales/refunds is not allowed.

| Metric | Definition |
|---|---|
| Gross merchandise value | Sum of original line quantity × selling price before discounts/tax for completed sales in the interval. |
| Net sales excluding tax | Original sale line net amounts in the interval minus completed return net amounts at their return completion times in the interval. |
| Net tax | Original collected tax minus completed refunded tax, using their respective event times. |
| Net collected payments | Original payment applied amounts minus completed refund amounts, grouped by method and event time. |
| Net COGS | Original sold quantity × cost snapshots minus cost of completed restockable returns, using each event's interval. Damaged returns do not reverse COGS under this baseline. |
| Estimated gross profit | Net sales excluding tax minus net COGS. Not net business profit and not a statutory financial statement. |
| Original completed sale count | Count of original completed sales in the interval; return events do not create a new sale or delete the original count. |
| Average transaction value | Sum of original completed sale grand totals in the interval divided by their count; return-adjusted totals are a separate metric. Zero count yields zero, not division failure. |
| Net product units | Original sold units minus completed returned units in the interval; may be negative for a return-heavy interval. |
| Current inventory valuation | Sellable quantities × current average cost at query time; not a historical end-of-period valuation. |
| Shift cash difference | Actual counted cash minus expected cash at immutable closure. |

Returns in October for September sales affect October event-based returns and net sales. A separate sale-detail view can show lifetime return totals for that receipt; do not mix the two definitions.

### 8.2 Snapshots and exports

Sales snapshot store identity/footer, cashier display name, terminal code, customer label, product SKU/barcode/name/unit, selling price, discounts, tax, original unit cost, and event time. Reprints use those snapshots and are marked as copies. Current logos may be stored as a versioned asset reference that is retained while receipts depend on it.

Report calculations use persisted business records, not mutable master prices. XLSX/PDF outputs use the same query/filter definitions as the API, with monetary totals and cost rounding displayed consistently. Escape spreadsheet cells originating from user input so they cannot become formulas. Export artifacts are permission-checked and expire after 24 hours; a download must recheck current user permissions. Version 1 can document a fixed public operational retention policy chosen before deployment; financial/domain records have no ordinary hard-delete action.

### 9.3 Database constraints and indexes

- MySQL 8.4/InnoDB baseline. Tests that prove locking behavior run against this engine.
- Unique SKU, non-null barcode, receipt/document numbers, scoped operation keys, one payment per sale, and one refund per completed request.
- Open-shift uniqueness must be enforced at database level, for example through nullable generated active-user/active-terminal keys with unique indexes, plus service locking. Test concurrent opening.
- Positive sale/receiving/return quantities; nonnegative stock, prices, tender, tax, and refund amounts. Adjustment deltas and cash differences may be signed. Validate document sums before commit.
- Restrict deletion for referenced products/users/customers/suppliers/terminals/documents. Archive master records instead. Draft deletion, if supported, cannot remove posted history.
- Index product lookups; sales `(completed_at, id)` and `(shift_id, completed_at)`; movements `(product_id, posted_at, id)`; returns `(sale_id, status)`; receiving supplier/reference; report event times; operation scope.
- Allowed state transitions occur through services. Do not expose general PUT endpoints that mutate posted amounts/statuses.
- Receipt numbers are unique server-generated identifiers, not client-provided values or `MAX(id)+1` calculations. A date prefix plus ULID/UUID-derived suffix or a locked sequence is acceptable; gaps are allowed.
- An audit log supports investigation but is not a replacement for sale, refund, inventory, or cash ledgers.

## 10. API and Frontend Contract

### 10.1 Transport and response conventions

Use `/api/v1` for product APIs. Session/CSRF routes may follow Laravel's native web route conventions. Serve the SPA and API under one HTTPS origin through a reverse proxy by default: frontend `/`, backend `/api/*`, `/auth/*`, and `/sanctum/*`. Subdomain deployments need an explicit cookie/CORS configuration review. Do not invent refresh-token rotation for this first-party session flow.

Successful response: `{ "success": true, "data": {}, "message": "...", "meta": { "request_id": "..." } }`.

Error response: `{ "success": false, "error": { "code": "INSUFFICIENT_STOCK", "message": "...", "fields": {} }, "meta": { "request_id": "..." } }`.

Use 401 unauthenticated, 403 unauthorized, 404 absent/hidden resource, 409 state/stock/quote/idempotency conflict, 419 CSRF/session mismatch where applicable, 422 invalid input, and 429 rate limit. Domain codes are stable. Lists are paginated, default 25 and maximum 100 rows, with allowlisted sorting/filter fields. Backend errors must not expose stack traces or SQL.

### 10.2 Required endpoint families

| Family | Required operations and authorization |
|---|---|
| `/auth` and `/me` | Login, logout, current identity/permissions, own profile/password; admin account lifecycle separately. |
| `/api/v1/settings`, `/terminals`, `/users` | Read permitted settings; owner settings/terminal/role management; cashier-account management as permitted. |
| `/categories`, `/products`, `/suppliers`, `/customers` | Permission-filtered list/detail/create/update/archive; product image upload; cashier customer search/create only. |
| `/shifts` | Open, own current, X report, close, Z report, privileged list/review, explicit assisted closure. |
| `/shifts/{id}/cash-movements` | Owner/manager cash in/out; append-only postings. |
| `/checkout/quotes` | Create a server quote; owned by current user/shift. |
| `/sales` | POST atomic checkout; GET filtered history/detail; GET permission-checked receipt. |
| `/checkout/recovery/{key}` | GET outcome for current user's checkout key; absent/pending/succeeded states. Absence is not permission to request external payment again. |
| `/operations/{operation}/{key}` | GET the current user's permitted posting outcome for refund, receiving, adjustment, stocktake, cash movement, or shift operation keys; enables unknown-outcome recovery without another external action. |
| `/sales/{id}/reprints` | POST audit a reprint request and return receipt representation; no new sale. |
| `/receivings` | Draft create/edit, post, cancel, list/detail. |
| `/inventory-adjustments` | Draft create/edit, post, cancel; owner-only revaluation subtype. |
| `/stocktakes` | Start/count edits/post/cancel/recovery with inventory guard. |
| `/return-requests` | Create/look up, approve/reject/cancel, complete with active shift and refund confirmation. |
| `/reports`, `/exports` | Permission-filtered reports; create export job, inspect status, download with reauthorization. |
| `/audit-events` | Owner or scoped manager read; no write/delete endpoint. |

All business POST actions capable of duplicate financial/inventory effects require scoped idempotency. Backend must provide an OpenAPI contract with payloads, data types, validation limits, error codes, and example responses before frontend integration for each delivered slice.

### 10.3 Frontend interaction rules

- Optimize the primary POS workspace for desktop and landscape tablet: scanner/search, product results, cart, and payment action are easy to reach. Use touch controls of at least 44×44 CSS pixels for primary actions.
- Smartphone layouts support readable management and occasional POS use; do not promise equal speed to a dedicated terminal. No clipped totals or unreachable payment controls at 360 px width.
- Preserve scanner focus appropriately; show unknown-barcode feedback; repeat scan increments quantity. Keyboard actions must not submit payment accidentally.
- Cart edits update an immediate client estimate; clearly distinguish it from the accepted server quote. Debounce searches and cancel stale requests; do not reload the whole page for each cart action.
- Keep checkout pending until outcome is known and prevent accidental double clicks. Recovery survives a page refresh. Cart persistence is scoped to current user/terminal and contains no customer personal information, tokens, or card data.
- Explicit logout clears local cart and cached private data. A session-expiry redirect may preserve only the scoped non-sensitive cart/key; another user cannot restore it. Successful recovery removes that cart once, not before the server outcome is known.
- Reject finalization while disconnected; show connectivity clearly. Do not present a locally retained cart as a completed sale.
- Private authenticated Next.js pages/API responses are not shared public cache entries. Server-rendered requests must preserve the correct session context; no cross-user caching of financial or personal data.
- Use Indonesian labels and `id-ID` formatting, keyboard-accessible dialogs, visible focus, field-specific validation, and errors that tell the operator how to recover. Framework/package names do not appear in cashier workflows.
- Follow installed antislop skills according to repository/session instructions; design decisions should support cashier actions rather than generic decorative dashboards.
